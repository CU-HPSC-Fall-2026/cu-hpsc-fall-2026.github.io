    "- There are different ways of how the overlap can be accomplished, known as progression strategies.\n",
    "- They fall under two categories: weak progression and strong progression"

    "## One-Sided MPI\n",
    "\n",
    "- What if we didn't need a \"hand shake\" for every communication?\n",
    "- What if we could simply \"put\" and \"get\" data in another rank's memory, like it was shared memory?"
   ]
  },
  {
   "cell_type": "markdown",

    "- Rank's create \"windows\" that serve as \"public\" memory accessible by other ranks\n",
    "    - Window is simply a buffer of memory somewhere\n",
    "    - The program provides the buffer to be used\n",
    "    - Window is created across all ranks which will participate\n",
    "- A rank can `MPI_Put()` and `MPI_Get()` to other rank's windows\n",
    "    - Must be coordination between ranks on who gets to put data in which area of window"

    "### Synchronization\n",
    "\n",
    "One-sided communication runs into a pretty similar issue as shared memory: **How do we know when we can safely read or write to shared/public memory?**\n",
    "- In other words, how do we guarantee correct ordering of the memory access?\n"
   ]
  },
  {
   "cell_type": "markdown",
   "id": "1aa83746-7b65-4f19-a86b-f1d433ac54f6",
   "metadata": {
    "deletable": true,

    "slideshow": {
     "slide_type": "slide"

    "tags": []

   "source": [
    "- One-sided MPI requires syncronization to accomplish this\n",
    "    - No such thing as free lunch, we'll still have to pay a bit to get our parallelization\n",
    "- In MPI documentation, these synchronizations separate Epochs; times where windows may or may not be written to\n",
    "\n",
    "![MPI Sync](../img/MPI_One-Sided_Sync_ENCCS.svg)\n",
    "- Green squiggles represent local computation\n",
    "- Synchronizations required for 2-sided communication of windowed data as well (e.g. collectives)"
   ]
  },
  {
   "cell_type": "markdown",
   "id": "a185a8bf-a48d-4669-a16d-d144feae283d",

   "source": [
    "- One-sided MPI has a few different syncronization options\n",
    "    - `MPI_Win_fence()`: Collective operation, effectively an `MPI_Barrier()`\n",
    "        - Every single rank with shared window synchronizes\n",
    "    - `MPI_Win_post()`, `MPI_Win_start()`, `MPI_Win_complete()`, `MPI_Win_wait()`: collective operation, more precise (not a blunt barrier)\n",
    "        - Allows you to differentiate between \"my window is ready to be read from\" and \"I'm accessing somebody else's window\"\n",
    "        - Specify exactly which ranks you need to syncronize with\n",
    "    - `MPI_Win_lock()`, `MPI_Win_unlock()`: non-collective operation, most efficient\n",
    "        - Target buffer not involved in syncronization at all\n",
    "        - This is NOT a lock/mutex/atomic on a remote memory region\n",
    "            - Similar functionality by specifying the lock as `MPI_LOCK_EXCLUSIVE`\n",
    "        - It applies to remote access only, not to the local window buffer"
   ]

    "### RDMA vs RMA\n",
    "- What we've described above uses remote memory access (RMA) semantics \n",
    "    - The CPU (be it the target rank or a dedicated process that MPI created) still handles the communication of memory to the NIC\n",
    "- This is better than 2-sided communication, but still not perfect\n",
    "    - We still have the overhead of handling the communication"
   ]
  },

   "source": [
    "Luckily, technology is cool.\n",
    "- Most modern networking solutions (for HPC, e.g. Infiniband) have remote *direct* memory access (RDMA) capability\n",
    "- They can read straight from physical memory, bypassing the CPU entirely\n",
    "    - Includes atomic memory operations and doing some collective operations in hardware rather than software\n",
    "- This means one-sided reads are \"free\"\n",
    "    - The NIC still has to process network requests, grab the data from memory, package it, and send it\n",
    "    - But the CPU doesn't have to do a thing!\n",
    "- RDMA is the ideal communication-computation overlap, as half the communication is completely independent of the MPI process"
   ]

    "## MPI+OpenMP (or MPI+Threads in general)\n",
    "\n",
    "- General idea is one MPI rank for each compute node (e.g. per shared memory region) and OpenMP threads for every core within that rank\n",
    "- Memory distributed inter-node, but shared intra-node\n",
    "- This way, we avoid the performance implications of distributed memory parallelism when on shared-memory systems!"
   ]

    "- Shared memory is conceptually simple, but **is still parallel programming**\n",
    "    - Shared memory still requires synchronizations and locks to maintain ordering\n",
    "    - Shared memory models often hide these issues, leading to many potential performance traps\n",

    "    - In fact, to get away from these issues, we often want there to be as little \"shared memory\" between threads as possible"
